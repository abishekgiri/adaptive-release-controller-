# GitHub event and timestamp semantics review

Review date: 7 September 2026. Scope: official GitHub documentation and the already archived three-development-repository pilot. No new repository observations or live enforcement tests. `ci-design-v1` remains unchanged.

## Evidence standard

A timestamp field, a notification, and a scheduler interlock are different things. A provider timestamp describes a recorded event; it does not prove when our collector knew it. A webhook describes an event that has occurred, not a promise that execution will wait for delivery. A configured interlock can hold a protected job independently of notification latency.

“Documented” below means the public documentation supports the stated limited meaning. Where creation/update fields are exposed without precise scheduler/instruction-level definitions, that uncertainty is explicit. Public docs and API examples do not identify the instant of the first user-controlled machine instruction. No unpublished server sequencing or latency guarantee is inferred.

## Field and event inventory

| Timestamp / event | Meaning, provenance and documentation strength | Before any user code? | Prospective observability, reliability and latency | Look-ahead risk / admissible use |
|---|---|---|---|---|
| Run `created_at` | Provider run-record creation field; exposed by run API. Exact scheduler ordering is not specified there. | Not a documented proof. | Can be read after record visibility; notification/REST delay is additional. | Identifier chronology only; never collector receipt. |
| Run `run_started_at` | Provider run-start field, attempt-sensitive. Run API example includes it while status is `queued`. | **No instruction-level guarantee.** | Present retrospectively; cannot treat its presence as advance notice. | In 227 scoped first attempts it equals creation; invalid as an assumed strict upper bound that must exceed creation. |
| Run `updated_at` | Provider update field. The docs do not define it as exclusive to terminal transition. | No. | Mutable snapshot available on API read. | Do not use as exact completion, historical visibility or immutable first label receipt. |
| Run status | API exposes lifecycle states such as queued/in_progress/completed and additional waiting/requested/pending states. No single universal linear transition sequence is established. | Queued/waiting alone do not prove all jobs have avoided execution. | Polls can miss states; asynchronous notifications can be stale when received. | A current state cannot reconstruct an earlier state or prove an enforceable pause. |
| Job `created_at` | Present in all 923 archived job objects. Interpreted as provider job-record creation; exact relation to queue insertion/allocation is not established by the published job API examples. | Unverified. | Existence can be read prospectively once exposed; no visibility lead time is guaranteed. | Retain source field; do not fabricate a queue-entry event. |
| Job `started_at` | Provider-reported job start in the job API. It is finer-grained than run start. | Not proof that no earlier job, runner hook or setup computation ran. | A start event is already at/after its boundary; receipt can arrive later. | Useful retrospective execution proxy; cannot certify an earlier observable decision window by itself. |
| Job `completed_at` | Provider-reported job completion. | No; terminal field. | Known on response/event receipt, after provider completion. | Eligible feedback for a job-specific target after receipt; maximum job completion is not run-label availability. |
| Step `started_at` / `completed_at` | Provider step lifecycle fields, including setup/post steps. | Only relative to that recorded step; earlier actions/hooks/setup may execute user-controlled code. | Retrospective step lists need not have been observable beforehand. | Do not label the first non-setup API row as a verified first user instruction. |
| Check-suite `created_at`, `updated_at` | Provider suite-record fields; suite groups check runs and can be created/rerequested through the API. Neither field defines one Actions job's execution boundary. | No universal guarantee. | Readable after suite visibility; event subscriptions differ by integration. | Do not join by SHA alone across suites, apps or attempts. |
| Check-run `started_at`, `completed_at` | Check integration can supply these fields through the Checks API. For third-party checks, these are reporter assertions, not universal GitHub runner clocks. | Depends on the producer; no universal guarantee. | API/webhook receipt remains separate. | Validate producer and exact check/job association; never assume any check timestamp is an Actions execution boundary. |
| Check-run creation/update times, if surfaced elsewhere | Integration/object lifecycle metadata; not a substitute when the specific REST representation omits them. | Unverified. | Endpoint/schema dependent. | Preserve nulls and provenance instead of synthesizing them from status. |
| `workflow_run` webhook | Activities include requested/in_progress/completed; requested is omitted on reruns. | Requested is not a reservation that delays execution. | Actions read permission plus configured subscription/receiver; asynchronous. | Save actual receipt and exact attempt; no earlier timestamp imputation. |
| `workflow_job` webhook | Job lifecycle notifications include queued/in_progress/completed. | Queued may precede that job's execution at generation; receipt need not. | GitHub documents autoscaling use and timeliness concerns. | Candidate observation channel, not a gate. |
| `check_suite` webhook | Suite activity; requested/rerequested require an appropriately permitted GitHub App. Repository/org hooks receive completed activity. | Completed is late; requested does not stop Actions. | Subscription and permission dependent. | A public read-only collector cannot assume a requested-suite stream. |
| `check_run` webhook | Check creation/completion/rerequest/requested-action activity, depending on subscription. | Creation is not an Actions scheduler barrier. | App/check dependent; notifications can lag. | Separate check producer, lifecycle and actual receipt. |
| Webhook delivery `delivered_at`, `duration`, `throttled_at` | GitHub delivery-attempt metadata, available through authorized hook-delivery APIs. | Not a user-code boundary. | Requires access to the configured hook; these are not generally public CI fields. | Useful transport audit; do not identify delivered_at with local durable receipt. |
| Local webhook receipt / durable archive time | Locally measured ingress and persistence timestamps; not supplied by the CI event. | Only if separately shown to precede the protected boundary. | Requires a running receiver, clock records and durable journal. | Correct local availability anchor; signature authenticates payload origin, not our clock accuracy. |
| HTTP `Date`, local request/response times | HTTP server response time and locally measured request interval. | No. | Available per request; cache/transport/process delays apply. | Not event creation time. Request duration is not webhook delivery latency. |
| Environment protection pending/approval | A configured platform rule prevents the protected job starting until requirements pass. | Before **that protected job**; earlier CI may already have run. | Observable via protection/review mechanisms; live operation here UNVERIFIED. | Legitimate boundary D; maintain protected artifact/job/attempt identity. |
| Self-hosted pre-job hook | Documented synchronous runner hook after assignment and before job execution; nonzero exit prevents that job. | Before job workload, but the hook itself executes controller/operator code. | Requires runner ownership/instrumentation; unavailable in this pilot. | Legitimate per-workload interlock, not evidence about GitHub-hosted first-instruction timing. |
| Organization audit events | Events such as job preparation and approval/rejection add administrative evidence. | Event-dependent; preparation/start records can be retrospective. | Requires organization permissions/stream access; no prompt public-delivery guarantee. | Supplemental audit only, not a new public preexecution trigger. |

## Why the old field mapping is unsupported

The official run-list example combines `status: queued` with equal creation/run-start timestamps. That is consistent with the pilot and contradicts the inference “run_started_at identifies the first user-code instruction.” It does not establish which internal phase that timestamp records. The correct response is to reject the stronger interpretation, not assign an earlier decision time or replace it with job start without validation. [Run-list example](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-repository).

For the earliest job boundary, all jobs in the attempt must be considered, including parallel jobs. A later test step or deployment job cannot establish that the entire workflow was previously unexecuted. Recorded setup rows and selected third-party actions also matter. Synchronous runner hooks provide a concrete example of code occurring outside a naive “first user run step” definition. [Runner hook semantics](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/run-scripts).

## Delivery and latency limits

GitHub explicitly warns that webhook deliveries may arrive out of order and may take minutes. That precludes treating a 2–12-second internal timestamp gap as a guaranteed external decision window. The documentation does not supply an event-to-controller latency percentile or maximum suitable for certifying this deadline. [Webhook troubleshooting](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/troubleshooting-webhooks).

The documented 10-second response deadline is the receiver's acknowledgment requirement after delivery; it is **not** a promise that GitHub delivers within 10 seconds. Failed deliveries are not automatically retried; reconciliation/redelivery must be arranged. [Webhook best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks), [failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries).

The archived pilot measured 240 local request-to-durable-receipt intervals: median 0.518 s, p95 2.671 s, range 0.364–3.165 s. These include GitHub CLI/process, network and persistence costs; they exclude event-to-poll waiting. They are not measurements of webhook latency, full feature readiness, policy computation or enforcement. See [timing evidence](timing/evidence/timing-summary.json).

GitHub timestamps in the sampled records have second resolution, while local receipts have finer display precision. Finer formatting does not establish clock synchronization. A future margin needs clock-offset/quantization uncertainty and a lower bound that remains positive after that uncertainty; zero/near-zero differences must not be classified as successful intervention.
