## Three access levels

| Level | Necessary access and owner role | Questions it permits | Questions it does not answer |
|---|---|---|---|
| **LEVEL 1 — observational only** | Owner-approved export or scoped reads of existing workflow/job attempts, exact workflow revisions, environments/protection configuration, review history, artifact/change joins and stage outcomes; export of all requests including rejected/missing where available | Validate endpoint meaning, historical selection/coverage, release and failure volume, contextual variation, and retrospective approved-case prediction **only where authentic historical feature availability can be established** | Does not prove contemporary API response times, sealed prospective snapshots, enforcement, denied counterfactuals, replacement-policy value or benefit to production |
| **LEVEL 2 — prospective instrumentation without changing decisions** | Level 1 plus passive event subscription/owner forwarding or bounded read-only polling; durable local receipt/processing timestamps; existing gate/reviewer/controller journal; read-only outcome reconciliation; authority to host the collector or owner runs it | Whether real requests can be observed and complete context sealed while the existing gate is held; prospective outcome completeness; later shadow prediction under unchanged reviewer practice if separately authorized | Does not validate our approve/deny actuator or improve decisions. Passive observation alone may miss fast approvals. No newly imposed hold, extra reviewer, auto-approval callback, score display or runner hook disguised as passive instrumentation |
| **LEVEL 3 — authorized intervention/enforcement testing** | Separate written test scope, owner/admin setup, eligible reviewer identity or protection App, isolated harmless environment, approved callback rights and independent execution witness; production access unnecessary | Engineering correctness of allowed approval/denial, latency, request binding and scoped nonexecution under tested conditions | A tiny test is not evidence of predictive value, beneficial operational decisions, complete bypass resistance, broad reliability or causal deployment benefit. Those require distinct studies |

Level 1 can begin by receiving an owner-produced sanitized export; handing research staff an admin token is unnecessary. Level 2 is the desired minimum for the proposed prospective prediction paper. Level 3 is **not a prerequisite to study prediction** if an already-operated gate can be reliably observed. Refusal of intervention therefore stops enforcement claims, not automatically observational research.

## Exact acquisition contract

These are required capabilities, not a request to grant every listed permission. Prefer an owner-operated exporter/collector and selected repositories. Documentation checked 2026-09-07; installation policy, GitHub product version and token identity must be verified with each owner before use.

[Environment API](https://docs.github.com/en/rest/deployments/environments) |

| Upstream test/check history | Only completed, actually received results tied to the released content; previous stage outcomes and receipt times | Actions metadata; `Checks: read` only if external check-run data is required, subject to owner approval |
| Passive webhooks | Required event payload subset, authenticated ingress, delivery ID, real local receipt, source hash and processing clock | Read-only GitHub App subscription or owner forwarding; repository webhook creation is a separate owner-controlled setup operation. `Webhooks: read/write` applies to repository-hook management/delivery inspection, not a blanket requirement for App subscriptions. [Webhook API](https://docs.github.com/en/rest/repos/webhooks) |
| Review/protection event coverage | Review decisions and request history for all eligible jobs; failed, absent and bypassed paths reconciled | GitHub documents `deployment_review` for GitHub Apps with `Deployments: read`; the reviewed default example shows approval. Do not assume every decision/transition is captured: verify supported event actions and supplement with owner journals and review-history reads. An ordinary repository webhook is not sufficient for this App-only event. [Event catalog](https://docs.github.com/en/webhooks/webhook-events-and-payloads#deployment_review) |
| Custom gate requests/callbacks | Existing protection App's request, binding, decision and callback journal | At Level 2, owner forwards existing records. Creating/enabling a new rule changes the gate and is Level 3. Custom-rule implementation uses `Deployments: write` and its registered App; currently documented as preview. [Custom rules](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/create-custom-protection-rules) |
| Approval/denial actuator | Exact authorized run/environment plus allowed job scope, reviewer eligibility and callback results | Level 3 only. Required-reviewer endpoint needs an eligible reviewer and `Deployments: write`; a write token alone is not reviewer authority. Do not confuse fork-run approval with deployment approval. [Review endpoint](https://docs.github.com/en/rest/actions/workflow-runs#review-pending-deployments-for-a-workflow-run) |
| Actual downstream consequences | Job endpoint validation; optional delivery, health, rollback and incident exports with declared coverage | Owner's read-only telemetry/export permissions; no production shell, credentials or customer records |

Do not assume every environment-protected job produces a deployment object. GitHub documents `deployment: false` with required reviewers, but says this setting is incompatible with custom protection Apps. The custom-request payload schema nevertheless permits a null deployment field. That schema alone does not establish a working custom gate without a deployment; record the documentation distinction and verify the selected mechanism/version with the owner. Preserve request/run/job/environment identity and reject ambiguous joins rather than inventing a deployment ID. [Environment/deployment distinction](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments#using-environments-without-deployments), [protection payload schema](https://docs.github.com/en/webhooks/webhook-events-and-payloads#deployment_protection_rule).

## Historical limitations and prospective prerequisites

The reviewed REST approval-history example includes environment creation/update timestamps, not a demonstrated per-review execution clock. Never relabel an environment timestamp as approval time. The pending endpoint describes **current** waiting environments; it is not by itself an archive of every former request. A public successful workflow with an `environment` key does not prove a meaningful approval barrier existed at the time.

For Level 2, require a receipt journal for required context and the existing admission event; immutable snapshot hash; conservative ordering against an owner-provided approval/release clock; complete outcome follow-up and outage reconciliation. A delayed webhook that arrives after approval cannot prove the gate was still held earlier. Sources with unknown timing stay invalid or missing. Do not prolong a live gate to make passive collection pass; report missed/late requests in the all-request denominator. [Timing review](../timing-boundary-review.md).

GitHub plan/repository visibility and organization policy may restrict relevant protections. The owner must confirm the existing configuration actually works; API availability alone is not evidence of participation or enforcement. [Deployment controls](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments).

## Minimum package needed before another empirical phase

1. One named cooperating owner with written scope and an existing real protected operation; a permission/export matrix signed off by that owner.
2. A data dictionary and small owner-approved, time-bounded sample spanning normal successes and available adverse/administrative states, with immutable joins and no outcome-selected cohort construction.
3. Complete aggregate request counts over a fixed window, including no-start, denied, cancelled and missing cases; event accrual estimate and independence map by service/team/organization.
4. A validated endpoint contract and a passive capture route capable of sealing features before **existing** approval, with no imposed delay.
5. Data-use/privacy terms and institutional ethics determination where applicable, before organization/user-level research data collection.
6. A revised precision/replication budget and explicit later ratification. Initial access to one owner permits an access/semantic pilot, not a general research conclusion.

No suitable package exists in current evidence. An owner export is a plausible route, not a demonstrated one. See [recruitment](recruitment-protocol.md), [outcomes](outcome-definition.md) and [stop criteria](stop-criteria.md).
